# growth-book-layout-spec —— 成长册 widget 网格版式契约

> 类型：**前端契约**。这是 `docs/frontend spec files/` 下的第一份，与同级 `docs/backend spec files/`（17 份，定义字段与 `ui=` 绑定）分工不同：backend spec 管**存什么**，本文管**画在哪、多大、怎么点**。
>
> 存在理由：成长册改 widget 网格之后，版式带上了一批数值要求（格数、边距、像素取整、最小触控尺寸、缩放倍率、DPI、精度门槛），这些在 backend spec 的 `field_key (中文名), cardinality, type|enum, ui` 记法里没有位置，写不进去；不写下来，编辑器会被实作错，而错的地方（例如格子不是精确正方）要到导出 PDF 才发现。
>
> **权威来源**：`../../../hualong-backend/DECISIONS.md` E3 及其下的 W1-W21。本文只是把已定的决策整理成可实作的形态，**不新增、不放宽、不引申**。与 `DECISIONS.md` 冲突时以 `DECISIONS.md` 为准。开放项见 §10，实作时不得自选一种读法默默补上。
>
> **本文不定义字段名与 `ui=` 标注**。控件命名权威仍是 17 份 backend spec 的 `ui=` 标注（见后端仓库 `CLAUDE.md`「UI 改版不得破坏数据映射」）。网格编辑器新增写入控件时，先在 `05 home-school-spec.md` 补 `ui=`，再重抽 `db/spec/ui-binding.tsv`，不要手改生成物。

## 1. 几何

### 1.1 版面单位

1.1.1 版面单位是**实体 A4 页**，纵向 **210 × 297mm**，不是连续画布（W1）。

1.1.2 **widget 不得跨页**，每个 widget 完整归属于单一页面。因此不存在切断、下推、留空洞这类分页副作用（W1）。

### 1.2 网格与边距

```
A4                210 × 297mm
左右边距          30mm   → 内容宽 150mm ÷ 15 = 10.0mm
上下边距          28.5mm → 内容高 240mm ÷ 24 = 10.0mm
网格              15 列 × 24 行，格子 10mm 精确正方，余数 0
内容区            150 × 240mm，占整页面积 58%
```

1.2.1 **几格就是几公分。** 15 可被 3、5 整除，24 可被 2、3、4、6、8、12 整除 —— 两轴都切得出对半与三等分（W1a）。

1.2.2 坐标域：`grid_x ∈ 0..14`、`grid_y ∈ 0..23`。**widget 不得放进边距**（W1b）。

### 1.3 上下为什么是 28.5 而不是 30

1.3.1 若四边都取 30mm，内容区为 `150 × 237mm`。`150 : 237` 约分为 `50 : 79`，**79 是质数**，所以四边都恰好 30mm 且格子精确正方的唯一整除解是 **50 × 79 格、格边长 3mm** —— 细到只能当定位网格用，不能当占格单位。

1.3.2 让上下各松动 1.5mm 之后，`297 − 28.5 × 2 = 240`，因数立刻好切：`240 ÷ 10 = 24`，与横向 `150 ÷ 10 = 15` 共用同一个 10mm 格边长。

1.3.3 左右 30 与上下 28.5 相差 1.5mm，肉眼无法分辨。**美术边框带按 28.5mm 设计即可**（W1a）。

### 1.4 边距是有功能的区域，不是余数

1.4.1 边距取约 30mm（而非 Word Normal 的 25.4 / 31.8）的理由是**要放得下美术边框**，太窄的花边塞不进去（W1b）。

1.4.2 后果三条：

| # | 后果 |
|---|---|
| 1 | 边框是**页版式库的一部分**，与该页版式一同存在版式库 JSON 里，且必须跟着进 PDF（W19，详见 1.4.3） |
| 2 | 网格只覆盖内容区，widget 不得越界（同 1.2.2） |
| 3 | 内容区只占整页 58%。**若美术边框最后没做出来，整本册子会看起来很空** —— 30mm 白边在幼儿纪念册上偏保守。边框素材是这个决定的前提，不是选配 |

1.4.3 **美术边框归我们（developer），不归园所**（W19）：封面图是**内容**（一张园所或班级的照片，admin 换得有道理），边框是**设计**（框住每一页）。依 W13 一贯原则 —— 版面品质由我们负责、不交给使用者 —— 边框放在页版式库 JSON 里（§7.3.3），**不提供上传入口，因此不由 `file_id` 管理、也不与班级模版绑定**。若要推翻，会多出一个 admin 端的素材管理入口（W19 明列的代价）。

## 2. 像素规则：任何 DPI、任何机宽下都精确正方

### 2.1 规则

```
cell   = floor(content_width_px / 15)      ← 只算一次，两轴共用这一个整数
rows   = floor(content_height_px / cell)
余数   → 并入页边距（底部最多 cell − 1 px）
```

2.1.1 **两轴共用同一个整数格边长**，不要分别拿内容宽、内容高去除格数 —— 分别除会得到两个不同的浮点值，widget 的长宽比就不再是格数之比。

2.1.2 `rows` 的期望值恒为 **24**。实作应断言 `rows === 24`；不等于 24 表示渲染面比例不是 A4，属渲染面配置错误，**不得靠改网格迁就**。

### 2.2 为什么先算整数格边长

2.2.1 mm 换算出来的尺寸本来就不是整数像素：

| 尺寸 | DPI | 像素 |
|---|---|---|
| 9.5mm | 300 | 112.2 |
| 10mm | 300 | 118.1 |
| 10mm | 150 | 59.06 |

2.2.2 所以不能「先把 10mm 换成像素再铺格」—— 每格摊到 0.06px 的误差，铺 24 行就是 1.4px 的累积漂移，而且横纵累积量不同，格子不再是正方。先取整数格边长、再把余数并进边距，误差被一次性挤到边距里，格子本身零误差。

### 2.3 工作示例（150 DPI，PDF 导出档）

```
A4 @150DPI        1240 × 1754 px
内容宽            150mm → 886 px
cell              floor(886 / 15) = 59 px
内容高            240mm → 1417 px
rows              floor(1417 / 59) = 24        （24 × 59 = 1416）
余数              1417 − 1416 = 1 px → 并入下边距
```

格子为 59 × 59 px，精确正方；渲染侧的唯一容差是页面底部最多 `cell − 1` 个像素的余量（W1a）。

## 3. 精确正方为什么是承重的，不是美观问题

3.1 **widget 的长宽比 = 占格数之比，必须逐像素成立**（W1a）。

```
2 × 2  = 精确 1:1
6 × 4  = 精确 3:2
```

3.2 教师拉一个 2 × 2 的图片 widget，语义是「这里要一张 1:1 的照片」。**家长端的裁剪框直接吃这个比值**（W10）—— 家长在手机上裁好的就是最终成品，服务器不留原图（W17）。

3.3 若格子只是近似正方，2 × 2 拉出来的其实是 1:1.01，家长裁的成品与框对不上，而且**没有原图可以重算**。整套「占几格即决定长宽比」的设计原理失效。

3.4 因此 §2 的整数格边长规则不是优化，是正确性要求。

## 4. 交互

### 4.1 最小 widget 尺寸 2 × 2

4.1.1 最小尺寸 **2 × 2 格（20 × 20mm）**。后端存档校验 `grid_w >= 2 AND grid_h >= 2`（W1c）。

4.1.2 理由：手机宽 390pt、页面 best-fit 时每格仅 **18.6pt**（`390 × 150/210 ÷ 15`），远低于 iOS 建议的 44pt 最小点击目标。1 × 1 的 widget，四角缩放把手的触控热区会互相重叠。

### 4.2 允许缩放（推翻「手机端不允许横向滑动」）

4.2.1 原规则要求画面宽度 best-fit 屏幕，代价是格子被压到十几 pt，教师点不准。**W1c 取消该规则，改为允许 zoom。**

4.2.2 数字：

| 量 | 值 |
|---|---|
| best-fit（390pt 视窗）时每格 | 18.6pt |
| 达到 44pt 所需倍率 | **2.37×** |
| 该倍率下可见的页宽比例 | 约 **42%** |
| 任何触控舒适倍率下的可见格数 | 约 **9 格**（390 ÷ 44 = 8.86） |

4.2.3 「约 9 格」是**与总格数无关的常数**。所以格数决定的不是「看得到几格」，而是「这 9 格占整页多少」。15 × 24 的一屏 9 格 ≈ **页宽 42%**（与 4.2.2 表同一口径：9 × 10mm = 90mm，占 A4 页宽 210mm 的 42%）；换成更细的网格只会让同一屏看到的实体面积更小。

### 4.3 缩放带来的三条互动要求

允许缩放之后，下面三件事**必须有实作**，缺一项编辑器就不可用：

4.3.1 **平移与拖曳 widget 的手势必须能区分。** 例如：单指拖动 = 平移画布，长按后拖动 = 抓取 widget，双指 = 缩放。方案由前端定，但不得出现「想平移却把 widget 拖走了」。

4.3.2 **拖曳 widget 到视窗外时需边缘自动卷动。** 在 2.37× 下只看得到 42% 页宽，没有边缘自动卷动就无法把一个 widget 从页首搬到页尾。

4.3.3 **重叠必须阻挡存档**（详见 §5）。

4.3.4 实作注记（事实对照，非决策）：现有原型 `screens/growth-book-edit.html`、`growth-book-sample.html` 的 viewport 声明为 `user-scalable=no`，且页面内没有网格。网格编辑器上线时该声明与 4.2 冲突，缩放需由页内实作提供，以免与 4.3.1 的手势区分互相打架。

## 5. 重叠

5.1 **重叠一律拒绝放置，不做弹开推挤**（W6）。iOS / Android 桌面那套弹性推挤在手机小屏幕上会造成连锁位移，教师看不懂发生了什么。

5.2 前端表现：放手时若与既有 widget 重叠，该 widget **标红 + 提示移走 + 关闭存档按钮**；坐标重叠时**拒绝存档整个栏目**（不是只丢弃那一个 widget）。

5.3 **服务端必须重做一次重叠校验。** 前端的标红与置灰存档按钮只是体验，**不是完整性边界** —— 同后端仓库 `CLAUDE.md` 安全红线的一般原则（客户端 UI 永远不是安全边界）。

5.4 页版式库 JSON 同样受此约束，由校验工具（暂名 `check-layout.mjs`，待补）把关：坐标落在 `0..14 / 0..23` 内、同页 widget 不重叠、最小 2 × 2、`binding_key` 在登记表内、宣告容量与实际槽位数一致（`GAPS.md` G29-4）。

## 6. widget 模型

### 6.1 只有两型

6.1.1 **图片、文字，两型，不做视频**（W7）。

6.1.2 **不为同功能不同尺寸各开一个模板** —— 不要「2×2 图片元件」「2×3 图片元件」这种清单，一律是可自由缩放的通用 widget（W7）。

### 6.2 存储形态

6.2.1 **一个 widget 一列，不存 JSON 数组**（W5）。这里刻意不套用后端「瘦关联表改 JSON」的一般偏好（`DECISIONS.md` B3），理由是 widget 有真实生命周期（新增／移动／缩放／删除）、要被逐一查询，而且**素材提交必须外键指向它**；若布局存 JSON，`widget_id` 就是数组元素、无法被外键指向，删 widget 会留下孤儿提交。

6.2.2 `db_book_widget` **只存新增栏目的 widget**；预设页的 widget 在页版式库 JSON 里（W13）。

### 6.3 文字 widget 的控制项

6.3.1 基本控制项：**字级、对齐（居中／靠左／靠右）**，作用于**整个 widget**，落在 `config` 上。

6.3.2 进阶控制放**抽屉**（比照 Android 编辑器），需要的人才打开，不占界面（W8）。目前没有任何进阶控制项，抽屉不出现。

6.3.3 **`literal` 文字支持逐段套用加粗／斜体／颜色**（2026-08-02 评审扩充 W8）。`content` 由纯文字改存 run 数组 `[{t, b, i, c}]`，无样式的段落只有 `t`，与旧的纯文字向下兼容。

6.3.4 **字级与对齐不逐段可改 —— 这是 §6.5 的前提，不是偷懒。** CJK 字符在常规体与粗体下同为定宽，所以粗／斜／色不改变换行，`maxlength` 仍可由 `grid_w × grid_h × 字级` 推导；字级若逐段可改，容量就算不出来，§6.5.1 的「溢出结构上不可能」立刻失效。已登记的偏差：拉丁字母与数字在粗体下进阶宽度会变，中文文案不受影响。

6.3.5 颜色只给**园所调色板 6 色**（`#1a1916 / #189b91 / #067e76 / #f6762f / #3388fc / #868686`），不给自由取色 —— 整本册子视觉一致性风险最大的就是颜色。

6.3.6 **字族不出控件。** 两端必须载同一个字体档（§9.2），选型与授权是 §10.2 的开放项；粗体与斜体各需独立字体档，因此 6.3.3 把该项要采购的字体数从 1 个推到 3 个。

### 6.4 图片 widget 的显示方式

6.4.1 显示方式（`fill` / `cover` / 自动裁切）由**教师**在网格端决定，落在 widget 的 `config` 上（W9）。

6.4.2 家长上传时**不强制**符合该比例，但家长端附裁剪工具，上传时预览最终显示比例、可拖拽调位（W10）。

6.4.3 **但 6.4.1 只适用于不经成长册裁剪工具的来源**（2026-08-02 评审，登记 W9 与 W10 + W17 的冲突）：

| binding_key | 出不出显示方式 | 理由 |
|---|---|---|
| `collected` | **不出**，改出「征集比例」快捷值（1:1 / 4:3 / 3:4 / 3:2 / 2:3，均为整数格数） | 家长端裁剪框吃 `grid_w:grid_h`、裁好才上传、只存成品（W10 + W17），进册的图与框必定同比例，`fill` / `cover` / `crop` 三者结果完全相同，是死控件 |
| `class.material`、`child.task` | 出 | 这些照片不经成长册的裁剪工具，比例不定 |
| `child.assessment` | 不出 | 即时绘制的向量图，自动填满框（§9.4） |

6.4.4 若后端认为 W9 的「不强制符合比例」仍应对 `collected` 生效（例如允许家长跳过裁剪直接传原图），要改的是 W10 / W17，本文不自行改判。

### 6.5 文字长度：由框推导，溢出结构上不可能

6.5.1 **不定全局字数上限。** 前端依 `grid_w × grid_h` 与当前字级即时算出 `maxlength`，打满就打不下去。**溢出这件事从根本上不存在**，因此不需要缩字、裁切或报错的规则（W18）。

6.5.2 反方向是另一条规则，不是同一条：

| widget | 谁打字 | 规则 |
|---|---|---|
| `literal`（教师打）、`collected`（家长打） | 人 | 上限 = **框推导出来的 `maxlength`**。框决定字数 |
| `child.message`、`child.term_eval`、`child.task`（既有记录流进来） | 数据 | **反过来：框必须大于等于该来源的字数上限**。编辑器挡掉太小的框 |

6.5.3 两个边角：

- 教师打完字之后再把字级调大，已打的字就超出了。**必须挡住存档并提示，不可默默截断。** 截断是最不能接受的失效方式 —— 家长拿到的纪念册里寄语写到一半断掉。
- bound 型的最小框由来源上限决定，所以**那些上限必须在动手排页版式库之前先定死**。现状：`child.message` 已定 **300**；`db_parent_task_submission.submission_text` 现值 **1000**；`db_term_eval.eval_text` **未定**（`GAPS.md` G31）。不定就无法决定期末评估那一栏的框要多大。

### 6.6 内容来源

6.6.1 只用**一栏 `binding_key`**，不开第二栏 `content_source`。粒度（school / class / section / child / widget）、谁填、要不要入齐备判定、能配哪种型别，全部是绑定目标的固有属性，**查登记表即可，不在每一列上复写**（W11）。

6.6.2 登记表的权威定义在 `DECISIONS.md` W11，本文不复制（复制就会产生第二份可能过期的清单）。前端只需知道三件事：

- `literal` 是唯一内容真的存在 widget 列上的一种，其余都是指针；
- `collected` 会**触发家长端素材征集**，且**也吃文字**（家长打的字是 UGC，必须与照片走同一条内容把关）；
- `child.assessment`（五维雷达图）**不存任何文件、不存 base64**，两端即时算（见 §9.4）。

## 7. 页与栏目模型

### 7.1 页

7.1.1 **一个栏目可含多页**，页数由教师新增，不是固定 1 页（W2）。

7.1.2 widget 归属 `section_id + page_index + grid_x/grid_y/grid_w/grid_h`。

### 7.2 栏目

7.2.1 预设 6 项，**固定顺序**：`intro 园所介绍 → time 在园时光 → task 亲子活动 → term 期末评估 → comp 综合评估 → message 教师寄语`（E3-1）。

7.2.2 **不做整体拖拽排序**（纵向排序清单在手机上太笨重），故模版不需要 `sort_order`。新增栏目用 `anchor_after` 落位，值为 `'cover'` 或某预设 `section_key`（E3-2、W13）。

7.2.4 **`anchor_after` 可指向另一个新增栏目**（2026-08-02 评审，放宽 7.2.2）。原规则下两个新增栏目无法连排（想把「毕业典礼」放在「入学第一天」之后做不到）。取值扩充为 `'cover'` | 预设 `section_key` | **另一个新增栏目的 `section_id`**，连带三条：

- **成环必须挡住**：A 在 B 之后、B 又在 A 之后。前端在下拉选项里排除自己与所有（递归）锚定到自己的栏目；**服务端必须重做一次校验**，前端 UI 不是完整性边界（同 §5.3）。
- **删除不留孤儿**：删掉某栏目时，锚在它之后的栏目改锚到它原本的锚点。
- **落位是多轮扫描**：锚点本身可能还没落位，一轮扫不完；仍解不开的（数据层的环或悬空锚点）一律落到册尾，**不得让栏目凭空消失**。

7.2.3 新增栏目**不设上限**，前后端都不做数量校验（E3-5）。

### 7.3 网格适用全册，但预设页教师不能改

7.3.1 **网格适用全册**，预设 6 个栏目的页面同样是网格版面（W3）。

7.3.2 但预设页**由我们（developer）预先设计好，教师不提供修改**（W13）。「网格适用全册」不代表教师要从空白排整本。

7.3.3 两个层级，先前曾被混为一谈：

| | 谁作者 | 存哪 | 内容 |
|---|---|---|---|
| **页版式库** | 我们 | 后端仓库里的**版本化 JSON**，比照 `db/rubric/` 的地位 | 一批排好的页面版式，widget 坐标与 `binding_key` 都定好；美术边框也在这里 |
| **班级模版** | 教师 | DB | 启用哪些栏目、选哪套封面、新增栏目及其版面 |

7.3.4 教师能配置的只有三件事：**开关栏目、选封面、新增栏目**（新增栏目仍可自由排版）。**其中「选封面」已被 W19 收归 admin**（§7.4.1），故教师端实际是两件；另加「内容进不进册」（在园时光的成长资料收录排序、`亲子活动`的逐次勾选）—— 那两项不改版面，只决定灌进版面的内容，与本条不冲突。

7.3.6 **「新增栏目的版面编辑器」不在延后之列。** W4 说「尚未排期」的只有**我们用来编页版式库的范本编辑器**；教师端的栏目编辑器是同一套渲染、不同权限，且 `db_book_widget` 九列全部带 `ui=book_widget.*` 标注。原型已于 2026-08-02 落成 `screens/growth-book-section-edit.html`。放弃「可改但不建议改」的理由是那条路要付一整层代价：override 表、「还原预设」语意、班班版面分歧、我们更新版式库时谁跟得到谁跟不到；换来的是一个我们自己都不希望教师使用的功能。

7.3.5 版式库放 repo 不放 DB 的理由：后端 `CLAUDE.md` 红线 5 订明「生产环境所有业务表初始为空」。版式库若进 DB，它就是一类「必须存在于生产的产品参考资料」，那个仓库没有这个类别。代价是版式 JSON 由我们手动 commit，**不能热更新**（W13）。

### 7.4 归属层级

7.4.1 **封面归园所**（`db_school.book_cover`，只有 admin 能改）：同一所幼儿园发出去的纪念册封面应该长一样。

7.4.2 **栏目开关与新增栏目归班级**：那本来就逐班不同（「入学第一天」「毕业典礼」是班级记忆）（W19）。

### 7.5 草稿与定稿

7.5.1 `db_growth_book_template.template_status`：`d1=draft 草稿（可编、可预览）` / `d2=published 已定稿（冻结，册子依此生成）`（W16）。

7.5.2 同一套状态机也管素材征集 —— 两者是同一件事的两端：

```
草稿    栏目版面随便改，随时可预览整本的实际呈现
        ↓ 发布征集（教师有责任先看过预览）
已发布  该栏目版面冻结。不能改，只能撤回
        ↓ 撤回
草稿    该栏目已收的提交一并删除，重新发布时家长要重交
```

7.5.3 **系统不提供「发布了再偷偷改一下」的中间态。** 那正是会让家长交的裁切成品对不上框、而且无法重算的路径（W17 只存裁切成品，没有原图）。撤回的语意是**删除不是保留**，理由除了比例已失效之外，也符合 PIPL 第六条最小必要。

7.5.4 齐备判定 = 该栏目**全部槽位都有东西**，不是「至少交一件」。素材征集**以栏目为单位发起**（一个新增栏目 = 家长端一则待办，点进去列出该栏目所有页上的全部 `collected` 槽位，一次交完），不按 widget 发、也不按页发（W15）。

## 8. 不定长内容：重复页样板池 + 带种子的伪随机

### 8.1 问题

8.1.1 `child.task` `亲子活动`每名幼儿件数不同；`class.material` 在园时光虽是班级级一次挑定，但数量从 1 到上千都可能。**固定槽位接不住**（W14）。

### 8.2 做法

```
我们为该栏目设计 3-4 个页版式（各自宣告容量：这一版放 3 张 / 5 张 / 1 大张…）
渲染时系统挑版式、重复铺，直到盖完实际件数
挑选带随机性，避免整本每页长一样
```

### 8.3 种子必须持久化 —— 这不是选项

8.3.1 E3 第 11 点已定：**样本预览、单幼儿查看页、最终 PDF 必须同源渲染。** 若每次调用都真的随机，教师在预览看到的版面与导出的 PDF 不同，该条就破了。

8.3.2 所以要的是**带种子的伪随机**：

```
db_growth_book.layout_seed INT      -- 首次渲染时产生，之后永不变
挑选序列 = PRNG(layout_seed, section_key, page_index)
```

8.3.3 同一本册子重复渲染多少次都是同一个版面；不同幼儿因 `layout_seed` 不同而版面不同。

8.3.4 **PRNG 实作必须与绘图码同源**（§9.1 那一份），不得各端调用内建 `Math.random`：小程序端与 node-canvas 端必须产生同一个序列，否则 8.3.1 的要求在跨端时仍然破。

8.3.5 末页不满怎么配 —— **未定**，见 §10.1。

## 9. 渲染

### 9.1 一份绘图码，两个环境

9.1.1 **先定用途**：PDF 的目的是**传阅** —— 让没装这个小程序的亲友也能看，**不是拿去印刷店印实体册**。所以文字不需要向量、不需要 300 DPI（W20）。

9.1.2 **精度要求：像素级一致度 ≥ 95%（漂移 < 5%）。** 这条排除了「小程序用 WXML、服务器用 PDF 向量库」那种两套实作 —— 字体、行高、图片裁切的细节不可能对得那么齐。

9.1.3 架构：

```
版面绘制程序码    一份，写成针对 canvas 2D API
  小程序端        canvas 画 → wx.canvasToTempFilePath 逐页出 JPEG
                  → 自组极简 PDF（N 张 JPEG 各一页，结构简单，手写几百行，
                     不必把 pdf-lib 那 1MB 打进小程序包）
                  → wx.shareFileMessage 直接发到聊天
  服务器端        node-canvas 跑同一份程序码，只在批量导出时启动
分辨率            150 DPI，A4 = 1240 × 1754
```

9.1.4 **单本在客户端，批量在服务器。** 家长出自家孩子那本、教师预览，全部在手机上跑，**服务器零渲染成本**；只有教师的全班批量导出走服务器，一学期就那几次。因为两端跑的是同一份绘图码，这不算两套实作。

9.1.5 150 DPI 的依据：传阅是看屏幕，1240px 宽的 A4 已经很清楚；一页 2.1M 像素，旧手机内存吃得住（300 DPI 是 8.7M，逐页释放才勉强）。

### 9.2 字体：精度要求逼出来的硬需求

9.2.1 **唯一的漂移来源是字体。** iOS 用苹方、Android 用 Noto Sans CJK、服务器又是第三种，中文字宽不同会连锁影响断行，5% 守不住。

9.2.2 因此**两端必须载同一个字体档**（小程序侧用 `wx.loadFontFace` 载网络字体）。

9.2.3 CJK 字体 5-15MB，**需子集化**。

9.2.4 **字体授权从选配变成硬需求，且必须涵盖服务器端嵌入与再散布。** 选型与授权**未定**，见 §10.2。

### 9.3 图片

9.3.1 **只存裁切后的成品，不留原图**（W17）。家长在手机上裁好、上传的就是最终版。

9.3.2 统一转 **JPEG（MozJPEG 编码，q82-85）、长边 2000px**。

9.3.3 格式选 JPEG 的理由与压缩率无关：**PDF 原生支持的图像编码只有 `DCTDecode`（JPEG）与 `JPXDecode`（JPEG 2000）**，WebP / HEIC / AVIF / JPEG XL 一个都不在规格里。存 JPEG，嵌进 PDF 是 byte copy，零解码、零重编、零画质损失；存别的，每次生成 PDF 都要解码重编，批量导出是上千次转码跑在 2 核 VPS 上。

9.3.4 **输入端照单全收**：客户端传 HEIC / WebP / PNG 都接，服务器统一转。转码发生在上传当下一次，不在渲染时。

### 9.4 雷达图

9.4.1 五大领域均分完全由 `db_child_assessment_item` 的题项分推导（题项级均值），所以雷达图是**算出来的东西，不是一份素材**（W12）：

```
小程序端   canvas / JS 直接画
PDF 端     服务器绘向量，不是先产图档再贴图
落地       零文件、零 base64、零字段
```

9.4.2 同一条逻辑适用**所有** bound widget：它们在 `db_book_widget` 上什么都不存，一律即时读。widget 只记「这个盒子要显示什么」与「盒子多大」。

### 9.5 页数软上限

9.5.1 **软上限，超过只提示不阻挡**（W21）。硬上限会与 E3 第 5 点「新增栏目不设上限」直接矛盾，而且教师往往到最后一刻才撞墙，那时素材都征集完了。

9.5.2 **先撞墙的是文件大小不是渲染时间**：150 DPI 漫图 PDF 一页约 400KB，40 页 ≈ 16MB，167 页 ≈ 67MB。渲染时间反而还好（node-canvas 每页 100-300ms，30 本 × 20 页约 1-3 分钟）。

9.5.3 提示落点：成长册入口页的生成检查表、批量导出弹层。显示**预估页数与文件大小**。

9.5.4 门槛值暂以 **40 页 / 16MB** 占位，实际按 `wx.shareFileMessage` 的大小上限定 —— **待查证**，见 §10.3。
